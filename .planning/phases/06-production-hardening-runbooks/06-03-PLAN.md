# Plan 06-03: PostgreSQL/Redis Disaster Recovery Drill, Backup Restore Verification, and Production SLO Validation

<threat_model>
### Plan 06-03 STRIDE Threat Analysis

| Threat Category | Specific Threat Scenario | Mitigation in Plan 06-03 Architecture | Verification Mechanism |
|---|---|---|---|
| **Spoofing (S)** | Redis crashes and restarts cleanly with empty memory; quarantined malicious principals attempt access during cache reconstruction window. | Gateways fail closed (HTTP 503 `DEPENDENCY_OUTAGE_REDIS`) when Redis is down. Gateway readiness probe remains unready (503) until the DR reconstruction routine pulls active quarantines from PostgreSQL and repopulates Redis via `ReconstructQuarantines`. | Automated drill in `tests/dr/dr_test.go` asserting quarantined principal is blocked immediately upon service resumption. |
| **Tampering (T)** | PostgreSQL restored from point-in-time backup contains stale snapshot version $M < N$, causing split-brain or monotonic version rejection. | Disaster recovery reconciles snapshot version numbers: the control plane queries active gateway fleet acknowledgment versions upon reconnection and forces the next published snapshot to version $\max(N_{\text{gateway}}, M_{\text{db}}) + 1$. | Automated drill in `tests/dr/dr_test.go` verifying monotonic version continuity and snapshot acceptance. |
| **Repudiation (R)** | Gateway pod abruptly killed mid-traffic; uncommitted local WAL records are dropped or replayed with duplicate key errors. | Audit ingestion worker persists checkpoint progress in `wal.cursor`. On restart, it resumes from the recorded byte offset and flushes records to PostgreSQL using `ON CONFLICT (event_date, event_id) DO NOTHING` deduplication, ensuring zero audit loss and zero duplicate insertion crashes. | Automated drill in `tests/dr/dr_test.go` verifying crash recovery replay of uncommitted WAL records. |
| **Information Disclosure (I)** | Disaster recovery procedures or incident response runbooks document hardcoded production database credentials or private cryptographic keys. | All operational runbooks specify environment variable parameterization (`DATABASE_URL`, `REDIS_ADDR`, `KUBECONFIG`) and Kubernetes Secret references; hardcoded secrets are strictly prohibited. | Runbook documentation review and static assertion in automated tests. |
| **Denial of Service (D)** | Disk spool reaches 90% capacity during database partition, halting admissions (HTTP 503) to prevent un-audited forwarding. | Runbook `spool-saturation-recovery.md` establishes clear triage steps: worker scaling, segment offloading, dynamic PVC volume expansion, and emergency buffer draining to restore capacity below the 90% threshold. | Runbook validation and checklist verification against `internal/audit/spool.go`. |
| **Elevation of Privilege (E)** | Control plane severed by network partition; gateways fail open and evaluate outdated policy indefinitely without cryptographic lease. | Invariant 9 enforcement: Gateways require signed 10s freshness leases. If control plane is partitioned for $>60$ seconds, gateway readiness fails (HTTP 503) and requests fail closed (`LEASE_EXPIRED`). | Runbook `control-plane-partition.md` procedures and automated drill coverage. |
</threat_model>

## Executive Summary

Plan 06-03 validates the ultimate resilience, disaster recovery, and production sign-off requirements for the Aegis Distributed Zero-Trust Access Gateway (REV-03, AUD-01, DIST-01). In zero-trust architecture, catastrophic infrastructure events—such as full cache wipeouts, database point-in-time restores, or node crashes—must never compromise security invariants or result in unauthorized access.

This plan enhances `internal/revocation/store.go` with a high-throughput pipelined `ReconstructQuarantines` method that restores active principal bans with remaining TTLs in a single network roundtrip. It implements an automated disaster recovery integration suite in `tests/dr/dr_test.go` verifying three mission-critical recovery scenarios: Redis quarantine reconstruction, PostgreSQL point-in-time snapshot version reconciliation ($\max(N, M) + 1$), and local WAL disk spool crash recovery with idempotent deduplication. Finally, it authors six comprehensive SRE operational runbooks in `docs/runbooks/` covering incident response (SEV-1 to SEV-4), disaster recovery, emergency quarantine, 90% spool saturation, control plane partitions, and a formal production SLO release gate sign-off checklist.
