# Plan 03-03: Redis Atomic Token-Bucket Rate Limiting and <5s JTI Revocation / Principal Quarantine with Fail-Closed Semantics

<threat_model>
### Plan 03-03 STRIDE Threat Analysis

| Threat Category | Specific Threat Scenario | Mitigation in Plan 03-03 Architecture | Verification Mechanism |
|---|---|---|---|
| **Spoofing (S)** | Attacker presents a stolen or revoked JWT token, or a quarantined compromised principal attempts access before token expiry. | `internal/revocation/store.go` checks token `jti` and principal ID against Redis in a single pipelined roundtrip (<0.5ms); administrative writes block callers grid-wide in <5s with HTTP 403 (`TOKEN_REVOKED`, `PRINCIPAL_QUARANTINED`) (REV-03, ADR-0005). | Unit and security tests asserting HTTP 403 on revoked JTI and quarantined principal. |
| **Tampering (T)** | Attacker tampers with rate limit counters or manipulates key names to cause collision. | Key schemas are strictly scoped and sanitized (`ratelimit:{principal}:{route}`, `revocation:jti:{jti}`, `quarantine:principal:{id}`); atomic operations execute via certified GCRA Lua script in `redis_rate/v10`. | Unit tests asserting distinct rate limit buckets per principal and route. |
| **Repudiation (R)** | Revoked or rate-limited requests rejected without correlated audit tracking. | All rejection paths (HTTP 403 for revocation/quarantine, HTTP 429 for rate limit, HTTP 503 for Redis outage) populate audit completion context with explicit reason codes (`TOKEN_REVOKED`, `PRINCIPAL_QUARANTINED`, `RATE_LIMIT_EXCEEDED`, `DEPENDENCY_OUTAGE_REDIS`). | Unit and integration tests verifying audit event fields on rejection. |
| **Information Disclosure (I)** | Redis connectivity failures or timeout error messages leak internal cache connection strings or hostnames. | Gateway intercepts Redis errors and formats sanitized RFC 7807 problem details (`application/problem+json`) with standard type `https://aegis.local/errors/dependency-unavailable` without internal infrastructure details. | Negative test asserting sanitized JSON error body on Redis failure. |
| **Denial of Service (D)** | Distributed volumetric flood or credential stuffing attacks exhaust private backend microservice capacity. | `internal/ratelimit/limiter.go` enforces Redis GCRA token bucket rate limiting (default 100 rps, burst 200 per principal/route) returning HTTP 429 Too Many Requests with computed `Retry-After` header (REV-01). | Unit tests verifying burst threshold and rate throttling with `Retry-After` headers. |
| **Elevation of Privilege (E)** | Attacker deliberately DDoSes or partitions Redis to trigger permissive fail-open authorization and bypass token revocation. | All Redis calls on the request path are bounded by a strict 200ms context deadline (`context.WithTimeout(ctx, 200*time.Millisecond)`). If Redis is unreachable, errors, or times out, the gateway **fails closed** immediately with HTTP 503 Service Unavailable (`DEPENDENCY_OUTAGE_REDIS`). No permissive fallback is ever allowed (REV-04, Invariant 1, ADR-0005). | Security chaos test in `tests/failure/redis_outage_test.go` severing Redis connection; assert 100% of requests return HTTP 503 and zero reach backends. |
</threat_model>

## Executive Summary

Plan 03-03 implements distributed shared state for the Aegis gateway grid using Redis 7.2. In compliance with ADR-0005 and Invariant 1 (Default deny and fail closed), authenticating cryptographic credentials is supplemented with real-time distributed controls: distributed rate limiting, instantaneous token JTI revocation, and emergency principal quarantine.

This plan delivers a Generic Cell Rate Algorithm (GCRA) token bucket rate limiter via `go-redis/redis_rate/v10` enforcing per-principal and per-route rate limits with accurate `Retry-After` calculations. It introduces an ephemeral revocation and quarantine store utilizing pipelined Redis lookups achieving sub-5-second cluster-wide revocation convergence. Crucially, all Redis operations on the request hot path execute under a rigid 200ms context deadline; if Redis times out or suffers an outage, the gateway strictly fails closed with HTTP 503, eliminating any possibility of fail-open bypass during cache disruptions.

    - Writes `SET revocation:jti:{jti} "revoked" EX {ttl}` to Redis.
  - `QuarantinePrincipal(ctx context.Context, principalID string, reason string, ttl time.Duration) error`:
    - Writes `SET quarantine:principal:{principalID} {reason} EX {ttl}` to Redis.
  - `RemoveQuarantine(ctx context.Context, principalID string) error`:
    - Deletes key `quarantine:principal:{principalID}`.
  - `CheckRevocation(ctx context.Context, principalID string, jti string) (revoked bool, reason string, err error)`:
    - Bounded by strict 200ms context timeout: `context.WithTimeout(ctx, 200*time.Millisecond)`.

    - If principal quarantine exists: returns `true, "PRINCIPAL_QUARANTINED", nil`.
    - If JTI revocation exists: returns `true, "TOKEN_REVOKED", nil`.
    - If neither exists: returns `false, "", nil`.
    - If Redis errors or context deadline exceeded: returns `false, "", fmt.Errorf("revocation check failed: %w", err)` (triggering fail-closed handling).
- Administrative writes to Redis propagate to all replicas within seconds (<1ms in Redis, fulfilling the <5s requirement REV-03).
- Unit tests in `internal/revocation/store_test.go` using `miniredis/v2`:
  - Assert valid principal and JTI pass check.
  - Assert revoked JTI returns `true, "TOKEN_REVOKED"`.
  - Assert quarantined principal returns `true, "PRINCIPAL_QUARANTINED"`.
  - Assert un-quarantining restores access.
  - Assert expired key restores access automatically.
  - Assert simulated timeout or closed connection returns non-nil error.
- Unit test command exits with code 0:
  `go test -v -race ./internal/revocation/ -run TestRevocationStore`
</acceptance_criteria>
