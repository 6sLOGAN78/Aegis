# Plan 03-01: PostgreSQL Relational Schemas, Goose Migrations, and Control Plane Snapshot Repository

<threat_model>
### Plan 03-01 STRIDE Threat Analysis

| Threat Category | Specific Threat Scenario | Mitigation in Plan 03-01 Architecture | Verification Mechanism |
|---|---|---|---|
| **Spoofing (S)** | Unauthenticated database connection or client connecting with overly permissive credentials. | `internal/storage/db.go` configures service-scoped credentials using SCRAM-SHA-256 and connection pooling (`pgxpool.Pool`); data-plane gateways never connect directly to PostgreSQL (CTRL-01, Invariant 11). | Unit tests in `internal/storage/storage_test.go` verifying connection pool initialization parameters. |
| **Tampering (T)** | Operator or API client submits malformed route paths with traversal sequences or invalid Rego syntax into control plane drafts. | `internal/control/validator.go` validates route definitions against strict URL/path constraints and compiles Rego syntax via OPA SDK before persisting or publishing drafts (CTRL-01). | Unit tests in `internal/control/validator_test.go` asserting route path traversal rejection and invalid Rego syntax rejection. |
| **Tampering (T)** | SQL injection via route parameters, service IDs, or snapshot metadata. | All PostgreSQL queries in `internal/storage/*_repo.go` use parameterized queries with binary protocol binding (`pgx/v5`). Zero string concatenation. | Static analysis and repository unit tests with hostile SQL injection payloads in route and service fields. |
| **Repudiation (R)** | Schema modifications or migrations applied out-of-order or without tracking. | Schema versioning managed via `goose/v3` embedded migrations (`migrations/*.sql`) recording execution timestamps and version history in `goose_db_version`. | Unit tests executing `migration.RunMigrations` against test database or mock. |
| **Information Disclosure (I)** | Database connection strings or internal database error details leaked to callers on validation failure. | Database errors are wrapped in domain-specific sentinel errors; validation failures return sanitized structured reason codes. | Tests in `internal/control/validator_test.go` asserting clean error messages without SQL stack traces. |
| **Denial of Service (D)** | Unbounded connection growth exhausting PostgreSQL max connections under load. | `pgxpool.Config` configures explicit pool bounds (`MaxConns: 25`, `MinConns: 5`, `MaxConnLifetime: 1h`, `MaxConnIdleTime: 30m`). | Unit test verifying pool configuration parameters. |
| **Elevation of Privilege (E)** | Publishing an untested or syntactically invalid Rego policy that inadvertently permits unauthorized traffic. | Control plane validator requires Rego modules to pass in-memory dry-run evaluation and syntax compilation before draft activation (CTRL-01). | Test verifying invalid or empty Rego policies cannot produce publishable snapshots. |
</threat_model>

## Executive Summary

Plan 03-01 establishes the foundational storage and validation tier for the Aegis control plane. In accordance with CTRL-01 and Invariant 11, policy authoring, route catalog definitions, and historical snapshots are managed centrally in PostgreSQL 16, completely isolated from the data plane request hot path.

This plan installs the core Phase 3 Go dependencies (`pgx/v5`, `goose/v3`, `go-redis/v9`, `redis_rate/v10`, `miniredis/v2`, `pgxmock/v4`), introduces version-controlled database migrations creating the control plane schema (`services`, `routes`, `policy_drafts`, `snapshots`, `gateway_acks`) and daily range-partitioned audit table (`audit_events`), delivers high-performance repository interfaces with `pgxpool`, and implements the control plane draft validator ensuring that route definitions and Rego policy modules are validated and unit-tested before publication.
